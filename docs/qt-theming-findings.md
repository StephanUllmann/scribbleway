# Qt Theming / Icon Legibility Findings

Date: 2026-07-29
Status: Research / Not yet planned

## Context

Scribbleway's tray popup (`src/overlay/qml/FullRepresentation.qml`) is illegible under some system themes. The popup defines a local `theme` object that reads `palette.*` roles directly (`palette.highlight`, `palette.text`, `palette.midlight`, `palette.base`), and every button loads a bundled single-colour SVG via `icon.source` without ever setting `icon.color`. The SVGs themselves use `stroke="currentColor"` / `fill="none"`, Feather/Lucide style, with no other colour information. `ToolCursorBadge.qml` is the project's one existing precedent for opting out of the palette/icon system entirely and hand-painting fixed-colour chrome.

This document investigates, against primary sources (Qt 6 documentation at doc.qt.io, Qt source via codebrowser.dev, the Qt bug tracker, and the freedesktop XDG portal spec), what actually causes the illegibility and what the project's options are, given the hard constraint that **no new dependency may be added** — only plain `QtQuick`, `QtQuick.Controls`, `QtQuick.Shapes`, `QtQuick.Effects`, and `Canvas` are on the table, and the project's Qt floor is `QT_MIN_VERSION=6.6.0` (`CMakeLists.txt:8`), currently linking only `Qt6::Quick`, `Qt6::Qml`, `Qt6::Widgets`, `KF6::GlobalAccel`, `LayerShellQt::Interface` (`src/overlay/CMakeLists.txt:57-63`).

## 1. Palette: which `palette.*` roles are reliable, and is `midlight` one of them?

The QML `Palette` type exposes color-group properties (`active`/`disabled`/`inactive`, each a `ColorGroup`) and states only that "the colors that are not specified are initialized from `SystemPalette`, or potentially the Qt Quick Controls style" — [Palette QML Type](https://doc.qt.io/qt-6/qml-qtquick-palette.html). It does not enumerate per-role platform guarantees.

The individual roles are documented on `ColorGroup` — [ColorGroup QML Type](https://doc.qt.io/qt-6/qml-qtquick-colorgroup.html) and, at the C++ level, `QPalette::ColorRole` — [QPalette Class](https://doc.qt.io/qt-6/qpalette.html). Both classify `midlight` the same way:

> **midlight**: "Between `button` and `light`." (ColorGroup docs)
> **Midlight**: "Between Button and Light." (QPalette docs)

`midlight`/`Midlight` is grouped by Qt's own docs under "3D bevel and shadow effects" alongside `light`, `dark`, `mid`, `shadow` — i.e. it is a role designed for drawing raised/sunken widget bevels in classic (Windows-95-style) 3D controls, not a general-purpose "hover background" role. Neither doc page states that `midlight` is guaranteed visually distinct from `base`/`window` — Qt's own text is explicit that **no role differentiation is guaranteed at all**: the `QPalette` docs carry only a generic warning that "some styles do not use the palette for all drawing, for instance, if they make use of native theme engines. This is the case for both the Windows Vista and the macOS styles" ([QPalette Class](https://doc.qt.io/qt-6/qpalette.html)). Beyond that, **the docs do not state** which roles are guaranteed non-degenerate (i.e. not silently collapsed to the same color as a neighboring role) on any given style/theme. In flat, non-bevelled themes (Breeze, Adwaita) there is no documented guarantee that `midlight` differs perceptibly from `base`/`window` — it is a legacy 3D-shading role that flat themes have no strong reason to populate distinctly.

### How the palette actually gets populated, per platform

`QGuiApplication::palette()` states: "Roles that have not been explicitly set will reflect the system's platform theme" ([QGuiApplication Class](https://doc.qt.io/qt-6/qguiapplication.html)). "The system's platform theme" is a `QPlatformTheme` plugin, and on Linux this is **not part of Qt itself** — it is an out-of-tree plugin:

- On KDE Plasma, `plasma-integration`'s `KdePlatformTheme` reads the active Breeze/Plasma color scheme and populates `QPalette` from it — [KDE plasma-integration source](https://github.com/KDE/plasma-integration/blob/master/qt6/src/platformtheme/kdeplatformtheme.h).
- On GNOME, `QGnomePlatform` "sets the Adwaita-qt color palette to each Qt app so applications can use QPalette API to access colors used in the style" — [QGnomePlatform](https://github.com/FedoraQt/QGnomePlatform). This plugin is **not bundled with Qt** and is not guaranteed present on every GNOME install; without it (or without `xdg-desktop-portal-gtk` wiring in via a generic GTK theme plugin), a Qt app on GNOME falls back to Qt's built-in generic/default palette rather than actual Adwaita colors.

On top of the platform theme, which style renders the control matters (Qt Quick Controls, not Widgets):

> "If no style is explicitly set, a default style will be used. The style that is used depends on the operating system: Android: Material Style, iOS: iOS Style, **Linux: Fusion Style**, **macOS: macOS Style**, **Windows: Windows Style**. For all other operating systems, the Basic Style is used." — [Qt Quick Controls Styles](https://doc.qt.io/qt-6/qtquickcontrols-styles.html)

The Basic style's own doc page gives essentially no theming/palette details at all beyond describing itself as "a simple and light-weight all-round style" built for performance — [Basic Style](https://doc.qt.io/qt-6/qtquickcontrols-basic.html). **The docs do not state** how Basic sources its colours; this is moot for this project in practice since Linux (this project's primary target) defaults to Fusion, not Basic, per the platform-default table above — Basic only applies on "all other operating systems" not named in that list.

Fusion (the Linux default) is explicitly palette-driven: "The Fusion style uses the standard system Palette to provide colors that match the desktop environment" and "automatically switches dark and light themes according to the system settings" — [Fusion Style](https://doc.qt.io/qt-6/qtquickcontrols-fusion.html). This is the mechanism by which this project's popup (running under Fusion by default on Linux, unless overridden) is expected to pick up Breeze/Adwaita colors, and it explains why the bug is specifically about *legibility under some themes* rather than total failure: the roles it queries are populated, just not necessarily distinct from one another.

macOS Style and Windows Style are different in kind: both doc pages state, near-identically, "the style will follow the theme and colors configured globally from [System Preferences / Windows Settings], and does not come with a separate customization API on top of that," and "is not suitable for customizing" because "it sometimes draw[s] both the contents and the background onto a single background item" — [macOS Style](https://doc.qt.io/qt-6/qtquickcontrols-macos.html), [Windows Style](https://doc.qt.io/qt-6/qtquickcontrols-windows.html). This describes how the *native* controls (`Controls.Button` etc.) get their look — via platform drawing, not necessarily by populating discrete `palette.*` roles for arbitrary custom-drawn QML. **The docs do not state** whether hand-drawn `Rectangle`/`Text` elements that read `palette.midlight` or `palette.base` directly (as this codebase's `theme` singleton does) receive values that are kept in sync with `NSColor`/`UxTheme` on macOS/Windows the way Fusion's palette is kept in sync with Breeze/Adwaita on Linux — this is a gap in the documentation, not something we could establish from a primary source either way.

**Summary for Q1:** `palette.*` roles are populated from a real platform theme source on Linux (Fusion style + `QPlatformTheme` plugin, e.g. `plasma-integration` on KDE), but that plugin is third-party/out-of-tree and its presence is not guaranteed by Qt itself. `palette.midlight` specifically is documented only as a legacy 3D-bevel role ("between button and light") with no distinctness guarantee versus `base`/`window` on flat themes — this is a plausible root cause of poor hover-state contrast independent of the icon issue. macOS/Windows native styles are explicitly undocumented for custom (non-Control) palette consumption — the docs do not state this.

## 2. Icon recolouring: what does `icon.color` actually do, and does it matter?

### `icon.color`: default value and mechanism

`AbstractButton`'s grouped `icon` property documents `icon.color` as: "This property holds the color of the icon. The icon is tinted with the specified color, unless the color is set to `"transparent"`" — [AbstractButton QML Type](https://doc.qt.io/qt-6/qml-qtquick-controls-abstractbutton.html). The **default value is `Qt::transparent`**, confirmed directly in the `QQuickIconPrivate` source: `QColor color = Qt::transparent;`, and `resetColor()` restores this same value — [qquickicon.cpp via codebrowser.dev](https://codebrowser.dev/qt6/qtdeclarative/src/quickcontrolsimpl/qquickiconimage_p.h.html). Because this codebase never sets `icon.color` on any `Controls.Button`/`Controls.ToolButton`, every icon in the popup is running with the "no tint" default today.

The actual recolour mechanism, when `icon.color` *is* set, is implemented in `QQuickIconImage`'s pixmap-change handler:

```cpp
QPainter painter(&image);
painter.setCompositionMode(QPainter::CompositionMode_SourceIn);
painter.fillRect(image.rect(), color);
```

(quoted from `qquickiconimage.cpp` via [codebrowser.dev](https://codebrowser.dev/qt6/qtdeclarative/src/quickcontrolsimpl/qquickiconimage.cpp.html), and only applied when the color's alpha is greater than 0 — i.e. `Qt::transparent` genuinely means "skip this pass"). `CompositionMode_SourceIn` keeps the destination's **alpha channel only** and fills every non-transparent pixel with the flat `icon.color`. This means:

- **(a) It is a literal raster compositing operation on the already-rendered pixmap**, not a CSS/SVG-level color substitution and not a QIcon-theme mechanism.
- **(b)/(c)** It operates *after* the SVG has already been rasterized by QtSvg, so it is completely indifferent to whether the source SVG used `fill` or `stroke`, or whether it used `currentColor` at all — by the time `icon.color` runs, only the alpha shape of the rasterized icon matters.
- **(d) Multi-colour SVGs get flattened to one flat colour** — `SourceIn` overwrites every opaque pixel's RGB uniformly, so any original multi-colour information is destroyed if `icon.color` is set. Qt's docs do not describe this explicitly as "flattening," but it follows directly from `SourceIn` semantics and is corroborated informally on the Qt Forum, which notes `IconImage`/`ColorImage` exist "to colorize images properly in a simple declarative way" without documenting multi-colour behavior in more detail — [IconImage and ColorImage current state](https://forum.qt.io/topic/162273/iconimage-and-colorimage-current-state) (forum source, not authoritative — flagged as such since Qt's own docs are silent on this point).

### Does QtSvg support `currentColor`? — this is the crux

Qt's SVG support is not a full SVG 1.1/2.0 implementation. As of Qt 6.7, QtSvg extended its historical **SVG Tiny 1.2** baseline with a curated set of SVG 1.1/2.0 elements (`<symbol>`, `<marker>`, `<pattern>`, `<mask>`, `<filter>` and six filter primitives), explicitly "not to be compliant with SVG 1.1 or 2.0, but to deal with the most common stuff our users see," limited "to the most popular use cases and in particular to static elements" — [Qt SVG: Not so 1.2 Tiny any more (qt.io blog)](https://www.qt.io/blog/qt-svg-not-so-1.2-tiny-any-more). Neither Qt's official SVG module docs ([Qt SVG](https://doc.qt.io/qt-6/qtsvg-index.html)) nor this blog post mention `currentColor` as a supported feature.

We could not find an authoritative Qt documentation page stating outright "`currentColor` is unsupported" — **the docs do not state this explicitly, one way or the other.** The best evidence is from the Qt Forum and the Qt bug tracker, which we treat as secondary but note per the task's instruction to say so explicitly when a stronger primary source is unavailable:

- A Qt Lifetime Champion states plainly on the forum: "QtSvg does not support this [`currentColor`] yet. There is also a bug report about this," adding that without support, an icon using `currentColor` "displays in black rather than inheriting the parent widget's color," and the only workaround offered is to rewrite the color into the SVG file on disk before loading it — [How to load an SVG icon in QIcon with currentColor support?](https://forum.qt.io/topic/161571/how-to-load-an-svg-icon-in-qicon-with-currentcolor-support).
- The Qt bug tracker has at least one confirmed, fixed defect specifically about `currentColor` handling inside SVG **gradient** stops: **QTBUG-141102**, "[REG 6.9->6.10] SVG has wrong color" — a yellow-glow gradient using `currentColor` rendered as **black** in Qt 6.10.0, fixed in 6.10.1 (2025-11-20) and 6.11.0 Beta3 (2026-02-18) — [QTBUG-141102](https://bugreports.qt.io/browse/QTBUG-141102). This confirms that when `currentColor` resolution fails or regresses in QtSvg, the empirically observed fallback colour is **black**, not (for example) the pen/painter color passed to `render()`. Note this bug is about a regression that postdates this project's `QT_MIN_VERSION` floor of 6.6, so it does not itself establish 6.6's behavior — it is corroborating evidence for "unresolved `currentColor` → renders black," not proof of the specific defect in this codebase's Qt floor.

**On the fill-vs-stroke distinction specifically (task item 2c):** this codebase's icons use `stroke="currentColor"` with `fill="none"` — not `fill="currentColor"`. Per the CSS/SVG spec, `fill`'s initial value is black but `stroke`'s initial value is `none` (invisible). If QtSvg's parser, on failing to resolve `currentColor`, fell back to each property's *spec-defined initial value*, a `stroke="currentColor"` icon would render as **fully invisible** (`stroke:none`), not black — a more severe and different failure mode than "wrong colour, still visible." All of the corroborating black-fallback evidence we could find (the forum thread, QTBUG-141102) concerns `fill`, not `stroke`. **We could not find a primary or secondary source that specifically tests the `stroke="currentColor"` case**, so we do not assert which of the two outcomes (solid black, or fully invisible) actually occurs for this codebase's icons — this is a gap: **the docs do not state this**, and neither does any forum/bug-tracker source we located.

What we can say, as a labeled inference rather than an established fact: the reported symptom is "illegible under some themes" (implying the icons are *visible but wrong-coloured*, e.g. black-on-dark-background), not "icons don't render at all." That symptom shape is more consistent with a black-fallback than with a stroke:none/invisible fallback — an invisible icon would be reported as "missing," not "illegible." This is circumstantial reasoning from the bug report's own framing, not a sourced fact, and should be verified empirically (e.g. by screenshotting the popup under a dark Breeze/Adwaita theme) before being treated as confirmed root cause.

## 3. Contrast: does Qt provide anything for computing legible foreground-from-background?

The global `Qt` QML object's colour functions are: `Qt.rgba()`, `Qt.hsla()`, `Qt.hsva()`, `Qt.darker()`, `Qt.lighter()`, `Qt.tint()`, `Qt.alpha()`, `Qt.color()`, `Qt.colorEqual()` — [Qt QML Type (global object)](https://doc.qt.io/qt-6/qml-qtqml-qt.html). `Qt.darker()`/`Qt.lighter()` operate purely in HSV space on a single colour ("converts the current RGB color to HSV, divides/multiplies the value (V) component by factor and converts back to RGB") — they have no concept of a background colour or contrast ratio. None of the other functions compute luminance, contrast ratio, or "readable text colour."

`QColor` (the C++ type QML colours map to) similarly exposes only colour-space conversions and component accessors — [QColor Class](https://doc.qt.io/qt-6/qcolor.html) — no WCAG relative-luminance helper, no `qGray`-style perceptual-brightness-against-background utility, and no "pick readable foreground" method.

**Conclusion: nothing in Qt (QML or C++) computes WCAG-style contrast or derives a legible foreground colour from an arbitrary background.** This must be hand-computed in QML/JS if the project wants it — Qt does not provide it, and the docs do not suggest an undocumented equivalent exists.

## 4. Own-chrome escape hatch: what does ignoring the palette actually break?

### High-contrast / forced-colors support landed very recently, and after this project's Qt floor

Qt 6.10 added a `QStyleHints` "accessibility hints" property that "encapsulates platform dependent accessibility settings such as whether the user wishes the application to be in high contrast" — covering, per the Qt.io announcement: "On Apple platforms, the *Increase contrast* setting," "On Windows 11, a [Contrast theme]," "On the Gnome desktop, the *High Contrast* setting," and WebAssembly via CSS media queries — [High Contrast Mode in Qt 6.10 (qt.io blog)](https://www.qt.io/blog/high-contrast-mode-in-qt-6.10). Windows' underlying primitive is `SPI_GETHIGHCONTRAST` via `SystemParametersInfo`, which the Windows platform plugin now reads to populate this hint.

**This is decision-relevant: the project's `QT_MIN_VERSION` is `6.6.0` (`CMakeLists.txt:8`), and this high-contrast API is Qt 6.10+.** Reading OS-level high-contrast/forced-colors state is therefore not available at the project's current minimum Qt version without also raising `QT_MIN_VERSION` — itself a packaging/distro-support decision, separate from the "no new dependency" constraint but with similar practical weight. The blog does not explicitly enumerate KDE Plasma's high-contrast theme as a named case (only GNOME, Windows, and Apple platforms are named); **the docs do not state** whether/how KDE's high-contrast colour scheme is surfaced through this same hint versus simply appearing as an ordinary (if extreme) Breeze colour scheme via the normal palette path.

### Color-scheme (dark/light) support, and the freedesktop portal

Distinct from high-contrast, `QStyleHints::colorScheme` (`Qt::ColorScheme::Light`/`Dark`) plus `colorSchemeChanged` landed in Qt 6.5 — within this project's floor — [Dark Mode on Windows 11 with Qt 6.5 (qt.io blog)](https://www.qt.io/blog/dark-mode-on-windows-11-with-qt-6.5). On Linux, Qt integrates with the freedesktop XDG Desktop Portal Settings interface, whose `org.freedesktop.appearance` namespace defines:

> `color-scheme`: "0: No preference, 1: Prefer dark appearance, 2: Prefer light appearance"
> `contrast`: "0: No preference (normal contrast), 1: Higher contrast"

— [org.freedesktop.impl.portal.Settings](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.impl.portal.Settings.html). Whether a given Qt app actually receives these values depends on which portal backend (`xdg-desktop-portal-gtk`, `xdg-desktop-portal-kde`, etc.) is running and correctly implementing the Settings interface — not something Qt itself guarantees is present.

### What an own-chrome popup breaks

Given the above, a popup that hard-codes its own colours (the `ToolCursorBadge.qml` pattern: `Qt.rgba(0.08, 0.09, 0.12, 0.82)` background regardless of system state) breaks:

1. **OS forced-colors/high-contrast expectations** (Windows Contrast Themes, GNOME High Contrast, macOS Increase Contrast) — a user who has opted into a system-wide accessibility high-contrast mode for exactly the reason that default colours are illegible to them gets no benefit from that setting inside this popup, since it never reads `QStyleHints`' accessibility/contrast hint even where the hint exists (Qt 6.10+; not available at all below that).
2. **Platform HIG expectations that chrome tracks the system dark/light preference** — since `colorSchemeChanged` (Qt 6.5+, within this project's floor) is available and *not* used, an own-chrome popup would visually diverge from the rest of the desktop even though the mechanism to track it exists and costs nothing extra to link.
3. **No graceful degradation path** — a fixed palette cannot be "more" or "less" wrong under any given theme; it is uniformly indifferent to all of them, which is the current behavior of `ToolCursorBadge.qml` by explicit design ("pure geometry; no icon theme").

## 5. Does a running Qt Quick app re-theme live when the system palette flips?

Several distinct mechanisms, of different vintages:

- **`QGuiApplication::paletteChanged(const QPalette&)`** existed since Qt 5.4 but is **deprecated since Qt 6.0** in favour of `QEvent::ApplicationPaletteChange`, whose docs describe it as: "The default application palette has changed" (event value 38) — [QEvent Class](https://doc.qt.io/qt-6/qevent.html). `QGuiApplication::setPalette()` documents that "the color roles from this palette are combined with the system's platform theme to form the application's final palette" ([QGuiApplication Class](https://doc.qt.io/qt-6/qguiapplication.html)) — i.e. explicit app-level overrides and system-theme-derived values are merged, not one replacing the other outright.
- **`QStyleHints::colorScheme` / `colorSchemeChanged`** (Qt 6.5+, within this project's floor): "By default, this property follows the system's default color scheme... and changes when the system color scheme changes." Crucially: **"When this property changes, Qt will read the system palette and update the default palette, but won't overwrite palette entries that have been explicitly set by the application"** — [QStyleHints Class](https://doc.qt.io/qt-6/qstylehints.html). This is the clearest primary-source statement that **live re-theming without an app restart is a real, documented Qt 6.5+ capability**, not something the app has to poll or reconstruct manually — as long as the app hasn't explicitly pinned a palette entry itself (which would freeze that specific role).
- **The QML `palette` attached property itself**: `qml-qtquick-item.html`'s palette documentation states only that "items propagate explicit palette properties from parents to children" and that overriding a property on an item's palette "propagates to all of the item's children, overriding any system defaults for that property"; **it does not explicitly state whether a `palette.text`-style binding in a `Text` element automatically re-evaluates live when the system theme changes at runtime, versus only reflecting the palette snapshot taken at binding-creation time** — [Item QML Type, palette section](https://doc.qt.io/qt-6/qml-qtquick-item.html). This is a genuine documentation gap: **the docs do not state this explicitly.** Given `palette` is a QML property (and QML property bindings are live by construction, re-evaluating whenever any property they read changes) and given `QStyleHints` explicitly documents that the underlying default palette gets updated in place on a scheme change, the strong inference is that a plain `color: palette.text` binding does update live — but this is inference from adjacent documented behavior, not a direct statement we could cite.
- **Platform-specific caveat, historically KDE-specific**: a KDE Phabricator change (`D4492`, "[KHintsSettings] Emit `QGuiApplication::paletteChanged` when run as `QApplication`") shows that, historically, whether a KDE colour-scheme change actually triggered Qt's palette-change notification depended on KDE's own platform-integration code emitting the signal correctly — i.e. live re-theming on KDE has depended on the `plasma-integration`/`KHintsSettings` component doing its part, not purely on generic Qt behavior — [Phabricator D4492](https://phabricator.kde.org/D4492). This is a third-party source (KDE's own code review system, not Qt docs), included because it's the clearest evidence we found that live re-theming has platform-integration-plugin dependencies beyond Qt core, consistent with the palette-population findings in §1.

**Summary for Q5:** Live re-theming is a documented Qt 6.5+ capability via `QStyleHints::colorSchemeChanged`, which explicitly triggers a palette re-read that respects but doesn't clobber app-set overrides. Whether a bare QML `color: palette.text` binding picks this up automatically is not explicitly documented (only strongly inferable). On KDE specifically, correct live propagation has historically depended on `plasma-integration` emitting the right signal — another point where correctness depends on an out-of-tree platform plugin, not Qt alone.

## Available approaches under the no-new-dependencies constraint

Plain enumeration — no recommendation is made here; that decision belongs to a separate ticket.

- **Rely on `palette.*` bindings as-is (status quo for text/backgrounds).**
  Accuracy: depends entirely on the active `QPlatformTheme` plugin being correct and on the specific role chosen being one the active theme actually differentiates (§1 — `midlight` is not guaranteed distinct from `base`/`window`). Cost: zero, already in place. Accessibility: inherits whatever the system theme/high-contrast state provides, for free, on platforms/Qt-versions where that's wired up. New CMake link: none. Survives runtime theme change: yes for the palette mechanism itself (Qt 6.5+, §5), but only as good as the chosen role's contrast behavior under the *new* theme, which is exactly the current bug.

- **Set `icon.color` explicitly per button (e.g. to `palette.buttonText`/`palette.text`).**
  Accuracy: high for the icon-legibility part specifically — `icon.color` recolors via raster `SourceIn` masking (§2), which is completely indifferent to whether `currentColor` resolved correctly or not, sidestepping the QtSvg `currentColor` gap entirely. Cost: one property per button/ToolButton (and a different technique for the one plain `Image` delegate, which has no `icon` grouped property and would need e.g. wrapping in a `Controls.ToolButton`/`IconLabel`-equivalent, or one of the effect-based approaches below). Accessibility: as good as whatever palette role is chosen. New CMake link: none — `QtQuick.Controls` already imported. Runtime theme change: yes, if bound to a live palette role rather than a literal color.

- **Recolor via `QtQuick.Effects` `MultiEffect` (`colorization`/`colorizationColor`).**
  Accuracy: same flattening behavior as `icon.color` (single flat tint, §2), but works on the plain `Image`-based shape-list delegate too, where `icon.color` isn't available. Cost: one `MultiEffect` item wrapping each icon `Image`; "always enabled" so no extra shader overhead for colorization specifically ([MultiEffect docs](https://doc.qt.io/qt-6/qml-qtquick-effects-multieffect.html)). Accessibility: as good as whatever colour is fed in. New CMake link: not clearly required per available docs — `QtQuick.Effects` appears to ship within the already-linked Qt Quick/`qtdeclarative` module rather than as a separate `find_package` component, but **this is inferred, not confirmed by a primary source that states it outright**; also needs adding to QML import resolution since this project builds with `NO_IMPORT_SCAN` (`src/overlay/CMakeLists.txt:17`). Requires Qt 6.5+ (project floor is 6.6, so satisfied). Runtime theme change: yes, if `colorizationColor` is bound to a live palette role.

- **Hand-draw all glyphs as `Canvas`/`Shapes` geometry, following the `ToolCursorBadge.qml` precedent.**
  Accuracy: full control — colour is whatever's coded, no dependence on QtSvg's `currentColor` support at all. Cost: highest — every one of the ~15 bundled SVGs (`src/overlay/icons/*.svg`) would need re-expression as `Canvas` 2D calls or `Shapes` path data, and stays in sync by hand going forward instead of by editing an SVG file. Accessibility: only as good as whatever colour logic is written (manual, since Qt provides no contrast helper — §3). New CMake link: none — `Canvas` and `QtQuick.Shapes` are both allowed under the constraint. Runtime theme change: only if the hand-rolled colour is itself bound to a live palette role rather than hardcoded, in which case it's identical in spirit to the palette-binding approach, just for geometry instead of an `Image`.

- **Paint fixed own-chrome, ignoring the palette entirely (the current `ToolCursorBadge.qml` pattern, extended to the popup).**
  Accuracy: fully predictable and theme-independent by construction — cannot be "wrong" under any specific theme because it never reads one. Cost: low per-surface (one set of hardcoded colours), but throws away all theme integration work already present (`theme` singleton, `palette.*` reads) and must be manually re-audited for contrast once (no automatic per-theme correctness needed since there's only one state to check). Accessibility risk: highest of all options — per §4, it does not respond to OS-level high-contrast/forced-colors modes (Windows Contrast Themes, GNOME High Contrast, macOS Increase Contrast) even on Qt versions/platforms where Qt exposes that state, and diverges from the user's chosen dark/light preference on every platform, including ones where tracking it is free (`colorSchemeChanged`, Qt 6.5+, §5). New CMake link: none. Runtime theme change: does not apply — it is theme-independent by design, which is also its accessibility cost.

- **Compute contrast manually (WCAG-style relative luminance) and pick a foreground colour per background at runtime.**
  Accuracy: as good as the formula implemented; Qt provides no built-in for this (§3), so correctness is entirely on the implementer, including edge cases (e.g. semi-transparent backgrounds, animated theme transitions). Cost: a self-contained piece of JS/QML math (luminance + threshold), reusable across the popup once written. Accessibility: potentially the *most* robust of all options against unknown/future themes, since it reacts to the actual rendered background colour rather than assuming a given palette role is legible — but only mitigates the "wrong colour" failure mode, not the OS high-contrast/forced-colors integration gap from §4 (a manually-computed "legible" colour is still not the same thing as respecting a user's explicit forced-colors preference). New CMake link: none — pure QML/JS. Runtime theme change: yes, as long as it's recomputed from a live-bound background colour rather than cached once.

- **Some combination** (e.g. `icon.color`/`MultiEffect` bound to a manually-contrast-checked colour derived from the live palette, falling back to fixed own-chrome only for surfaces where no theme signal is trustworthy) — cost and accessibility profile is the sum/worst-case of whichever pieces are combined; not itself a distinct mechanism.
